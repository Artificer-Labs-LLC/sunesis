# SUNESIS — two engines, one witness

*SUNESIS (Greek σύνεσις: a putting-together — understanding as confluence) is
a free, open-source decompiler witness, built in public slices. This
repository is its first slice.*

Two independent open-source decompilers look at the same binary. Where
they agree, you get pseudocode with corroboration. Where they disagree,
you get a **graded disagreement record** — what kind of divergence it is,
how confident the classification is, which engine the evidence favours
and why, and the raw features both sides produced. Identification of
library code works the same way: every claimed name carries its match
evidence (hash values, similarity scores, tied candidates), never a
bare assertion.

This is a provider in the REA sense: it opens a binary by id
(`provider.json`: `two-engines`), does its work, and returns structured
evidence records with their limitations attached.

## What it does

Given an x86-64 ELF:

1. **Decompiles with both engines** — Kuna and Ghidra's decompiler
   (headless), independently.
2. **Identifies library functions** against a harvested corpus through
   three channels:
   - `fid-kuna` — Kuna's Function ID database, applied by Kuna itself;
     the provider diffs a FID-on listing against a FID-off listing, so
     every claimed rename is witnessed, not assumed.
   - `fid-ghidra` — Ghidra FidService full+specific hash pairs, looked
     up in a JSON index built from the corpus the same way.
   - `bsim` — BSim feature vectors (generated by Ghidra's own BSim
     tooling) compared by exact cosine similarity, locally.
3. **Grades disagreement** per function: `call_set`,
   `control_structure`, `type_signature`, `rendering`, `engine_gap` —
   each with confidence, a favour verdict (or an honest `unresolved`),
   the rule that produced it, and the feature evidence.

## Quick start

```sh
# Requires: Kuna >= 1.833, Ghidra 12.1.x, JDK 21, python3.
export GHIDRA_INSTALL_DIR=/path/to/ghidra
export JAVA_HOME=/path/to/jdk21
python3 -m two_engines analyze <target-elf> --corpus corpus --out proof/run
# -> proof/run/report.json + report.md
```

## The corpus

`corpus/` is a *mini-harvest*, built locally by `harvest/`:

- zlib 1.3.1 from source, gcc at -O0/-O1/-O2;
- the distribution's zlib, plus curated subsets of the distribution's
  glibc and OpenSSL static archives;
- per build: object files, a Ghidra export, BSim signature XML, and
  hash indexes (`fid_index.json`, `two-engines.fid`).

What the harvest could *not* produce on the build machine (a second
compiler, a from-source glibc/OpenSSL) is recorded in
`corpus/SUBSTITUTIONS.md` — substitutions are documented, never silent.

## Proof

`tests/` holds a planted fixture: a small program with four custom
functions of known semantics plus real zlib/OpenSSL code, analyzed
stripped. `proof/` holds the end-to-end run and its audit against the
unstripped symbol oracle — including the misses. Read
`proof/PROOF.md` for the numbers and what they do and don't show.

## Honest limits (also attached to every report)

- BSim similarity is exact cosine over BSim's `lshcosine` vectors,
  without BSim's LSH indexing or significance weighting.
- BSim claims need ≥4 vector features and ≥0.9 cosine; exact ties
  between distinct functions are reported as ambiguous, never resolved
  arbitrarily. Some siblings (the hash `*_Update` family) are
  vector-identical — Function ID evidence discriminates there.
- The disagreement grader is deterministic and feature-based; a
  "favoured" engine is a heuristic verdict with its rule stated.
- Kuna's listing is captured after its FID pass; Ghidra's pseudocode is
  captured unidentified. That input asymmetry inflates measured
  divergence and is stated in every report.
